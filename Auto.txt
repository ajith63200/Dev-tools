AutoSys — A Complete Guide
What is AutoSys?
AutoSys (now called Broadcom AutoSys Workload Automation) is an enterprise job scheduling and workload automation tool. It allows you to define, schedule, monitor, and manage batch jobs across distributed environments — on-premises or cloud.
Think of it as a sophisticated cron, but enterprise-grade, with dependencies, monitoring, alerting, and cross-platform support.

Core Concepts
1. Job
The fundamental unit in AutoSys. A job represents a task to be executed — a shell script, command, file watcher, or box.
Three main job types:
| Type | Description |
| --- | --- |
| CMD | Runs a command or script on a machine |
| BOX | A container that groups related jobs together |
| FW (File Watcher) | Triggers when a file appears/changes |

2. Job Definition (JIL)
Jobs are defined using JIL — Job Information Language. This is AutoSys's DSL for describing jobs.
jil/* Simple command job */
insert_job: my_first_job
job_type: CMD
command: /home/user/scripts/run_etl.sh
machine: prod-server-01
owner: etluser
permission: gx, wx
date_conditions: 1
days_of_week: mon, tue, wed, thu, fri
start_times: "08:00"
description: "Daily ETL job"

3. Box Job (Grouping)
A box groups jobs and controls their collective execution.
jil/* Define the box */
insert_job: etl_pipeline_box
job_type: BOX
date_conditions: 1
days_of_week: all
start_times: "06:00"

/* Job inside the box */
insert_job: extract_job
job_type: CMD
box_name: etl_pipeline_box
command: /scripts/extract.sh
machine: etl-server
condition: success(load_job)   ← depends on another job

4. Conditions (Dependencies)
This is AutoSys's power feature — jobs can depend on other jobs.
jilcondition: success(job_A) and success(job_B)
condition: done(job_A) or failure(job_B)
condition: success(job_A) and notrunning(job_B)
| Condition | Meaning |
| --- | --- |
| success(job) | Job completed successfully |
| failure(job) | Job failed |
| done(job) | Job finished (any status) |
| notrunning(job) | Job is not currently running |
| terminated(job) | Job was terminated |

5. Job Statuses
| Status | Meaning |
| --- | --- |
| STARTING | Job is being initiated |
| RUNNING | Currently executing |
| SUCCESS | Completed with exit code 0 |
| FAILURE | Completed with non-zero exit code |
| INACTIVE | Not yet activated for the day |
| ACTIVATED | Waiting for conditions to be met |
| ON_HOLD | Manually put on hold |
| ON_ICE | Excluded from processing entirely |
| TERMINATED | Forcefully stopped |
| RESTART | Marked for restart |

Key Commands
sendevent — Trigger or control jobs manually
bash# Force-start a job
sendevent -E FORCE_STARTJOB -J my_first_job

# Put a job on hold
sendevent -E JOB_ON_HOLD -J my_first_job

# Release a job from hold
sendevent -E JOB_OFF_HOLD -J my_first_job

# Mark a job as success manually
sendevent -E CHANGE_STATUS -s SUCCESS -J my_first_job

# Kill a running job
sendevent -E KILLJOB -J my_first_job
autorep — Report on job status
bash# Check status of a specific job
autorep -J my_first_job

# Check all jobs in a box
autorep -J etl_pipeline_box -l

# Check job details (full)
autorep -J my_first_job -d

# List all jobs matching a pattern
autorep -J "etl_*"

# Show machine status
autorep -M all
jil — Create/modify job definitions
bash# Load a JIL file
jil < my_jobs.jil

# Delete a job
echo "delete_job: my_first_job" | jil

Tips & Best Practices

Always use BOX jobs to group related jobs — it makes dependency management and monitoring much cleaner.
Use autorep liberally for debugging — autorep -J jobname -d gives full detail.
Set max_run_alarm on all long-running jobs to catch hangs early.
Avoid hardcoding paths — use global variables or environment files.
Use calendars instead of hardcoding days_of_week for complex schedules.
Test JIL syntax in a non-prod environment before pushing to production.

ON_HOLD and ON_ICE both stop a job from running, but they differ in how the scheduler treats them and what happens when the condition is met.

ON_HOLD

"The job is paused but still watching."


The job is temporarily suspended.
AutoSys keeps evaluating its conditions (time, dependencies).
Once released (JOB_OFF_HOLD), the job immediately runs if its conditions were already satisfied during the hold period.
Used when you want to temporarily delay a job but not lose the trigger.

Real-world use: A job is scheduled for 9 AM but there's a server maintenance window. You put it ON_HOLD, maintenance completes at 9:30 AM, you release it — it fires right away.

ON_ICE

"The job is completely frozen — invisible to the scheduler."


The job is fully excluded from AutoSys processing.
AutoSys stops evaluating conditions entirely — time windows and dependencies are ignored.
When taken OFF_ICE, the job does not auto-trigger retroactively — it waits for the next scheduled cycle.
Used when you want to permanently or long-term disable a job without deleting it.

Real-world use: A downstream feed is decommissioned for a month. You put the dependent job ON_ICE so it doesn't clutter monitoring or generate false alerts.

Side-by-Side
| Feature | ON_HOLD | ON_ICE |
| --- | --- | --- |
| Conditions evaluated? | ✅ Yes | ❌ No |
| Auto-triggers on release? | ✅ Yes (if condition already met) | ❌ No (waits for next cycle) |
| Appears in monitoring? | ✅ Yes | ❌ Effectively hidden |
| Use case | Short-term pause | Long-term disable |
| Release event | JOB_OFF_HOLD | JOB_OFF_ICE |

Start With the Big Picture (Say This First)

"AutoSys follows a client-server architecture with three main layers — the Scheduler (brain), the Database (memory), and the Remote Agents (hands). Everything revolves around an event-driven model where jobs are triggered based on time, dependency, or external events."


The Core Components
1. 🧠 Event Server (The Brain)

The central scheduler of AutoSys
Constantly monitors the database for jobs that are ready to run
Evaluates time conditions, dependencies, and events
When a job's conditions are met, it sends a trigger to the appropriate agent
There is typically a primary + shadow Event Server for high availability


"Think of it as the conductor of an orchestra — it doesn't play any instrument itself, it just tells everyone when to play."


2. 🗄️ AutoSys Database (The Memory)

Usually an Oracle or Sybase database
Stores everything — job definitions, schedules, statuses, history, calendars, global variables
The Event Server reads from and writes to this DB constantly
All autorep queries and jil commands hit this database


"This is the single source of truth. If you want to know the status of any job, at any point in time, the answer is in this database."


3. 🤖 Remote Agent (The Hands)

A lightweight process installed on every target machine where jobs run
Receives execution instructions from the Event Server
Runs the actual command/script locally on that machine
Reports back status updates (RUNNING, SUCCESS, FAILURE) to the Event Server
No agent = no job execution on that machine


"The agent is the boots on the ground. The Event Server decides what to run, but the Agent is the one who actually does it."


4. 💻 Client Utilities (The Interface)
These are the tools you as an operator use to interact with AutoSys:
| Tool | Purpose |
| --- | --- |
| jil | Define/modify/delete jobs |
| autorep | Query job status and history |
| sendevent | Manually trigger events (hold, release, force-start) |
| AutoSys GUI / WAAE Web UI | Visual monitoring and management |

The Event-Driven Flow — Step by Step
Walk the interviewer through exactly what happens when a job runs:
1. DEFINITION
   Admin loads a JIL file → job stored in the Database

2. ACTIVATION
   At the start of the processing day, Event Server
   activates all jobs → status moves from INACTIVE to ACTIVATED

3. CONDITION CHECK
   Event Server continuously polls the DB:
   "Is it 5 AM? ✅  Is job_A successful? ✅  → Fire this job"

4. DISPATCH
   Event Server sends execution command to the
   Remote Agent on the target machine

5. EXECUTION
   Remote Agent runs the command/script locally
   Status updated to RUNNING in the DB

6. REPORTING
   Job finishes → Agent reports SUCCESS or FAILURE
   Event Server updates status in the DB

7. CASCADE
   Downstream jobs whose condition was success(this_job)
   now get activated and the cycle continues

Q1. What is the difference between FORCE_STARTJOB and CHANGE_STATUS to SUCCESS?
"This is a very important distinction in production operations.
FORCE_STARTJOB actually executes the job — it ignores all conditions, time windows, and dependencies and physically runs the script on the target machine. The job goes through STARTING → RUNNING → SUCCESS or FAILURE.
CHANGE_STATUS to SUCCESS is a paper update — it just changes the status in the AutoSys database without running anything. The script never executes.
I use FORCE_STARTJOB when the job genuinely needs to run. I use CHANGE_STATUS to SUCCESS only when the job's work was already done outside of AutoSys — for example, someone ran the script manually directly on the server — and I just need to unblock the downstream jobs.
The danger of misusing CHANGE_STATUS is serious — if you mark a job SUCCESS without the work being done, downstream jobs trigger on bad or missing data, which can corrupt an entire pipeline."

Q2. A job is stuck in RUNNING state for 5 hours but it normally completes in 30 minutes. What do you do?
"First I check whether the job is actually running or just showing RUNNING in AutoSys while the process is already dead on the server.
I SSH to the target machine and run ps -ef | grep scriptname to see if the process is truly alive. I also check the application log to see the last activity timestamp.
Scenario A — Process is dead but AutoSys still shows RUNNING:
This is a zombie status. The agent lost communication mid-execution. I kill it using sendevent -E KILLJOB and then restart after fixing the root cause.
Scenario B — Process is genuinely running but slow:
I check top, df -h, and iostat to see if there's a CPU spike, disk full situation, or I/O bottleneck. I check if there are any database locks or upstream feeds that are delayed.
Once I identify the cause — I either let it complete if it's close, or kill and restart with the issue fixed. I also immediately notify stakeholders about the delay and give a revised ETA.
This is also why I always recommend setting max_run_alarm on every critical job — it alerts you automatically when a job exceeds its expected runtime."

Q3. What happens to downstream jobs if an upstream job fails? How do you handle it?
"When an upstream job fails, all downstream jobs that have condition: success(upstream_job) will stay in ACTIVATED state — they're waiting, watching, but never triggering.
My immediate action is to run autorep on the entire box to map the full dependency chain and understand how many jobs are blocked and what the business impact is.
Then I have three options depending on the situation:
Option 1 — Fix and rerun the upstream job. Once it hits SUCCESS, downstream jobs auto-trigger naturally.
Option 2 — If the upstream job's work was done manually, I use CHANGE_STATUS to SUCCESS on it to release the downstream chain.
Option 3 — If the upstream job is irrelevant for today and downstream jobs can run independently, I FORCE_STARTJOB each downstream job individually.
The key decision factor is always — did the upstream job's data actually get produced? If yes, option 2 is safe. If no, option 3 is risky and needs business sign-off."

Q4. What is a BOX job and why do we use it?
"A BOX is a container job that groups related jobs together into a logical pipeline.
We use BOX jobs for three main reasons:
First — dependency management. Instead of writing complex cross-job conditions everywhere, you control the flow inside the box cleanly.
Second — collective control. You can put an entire BOX on hold, on ice, or force-start it as a unit — without touching each individual job.
Third — monitoring clarity. In a production environment with hundreds of jobs, grouping them into boxes like ETL_EXTRACT_BOX, ETL_TRANSFORM_BOX, ETL_LOAD_BOX makes it much easier to see where a pipeline is at a glance.
One important behavior — if box_failure is set to 1 on a job inside the box, a failure in that job marks the entire box as FAILURE and stops other jobs in the box from running. This is useful for critical jobs where there's no point continuing the pipeline if a key step fails."

Q5. Explain what a typical AutoSys production issue investigation looks like end to end.
"In production, when I get a failure alert, I follow a structured approach:
Step 1 — autorep -J jobname -d to get status, exit code, run times.
Step 2 — Check application logs on the target machine for the exact error.
Step 3 — autoping -M machinename to confirm the agent is alive.
Step 4 — Map downstream impact using autorep on the parent box.
Step 5 — Identify root cause — is it a script error, infra issue, data issue, or agent issue?
Step 6 — Fix the root cause. Validate the fix by running the script manually on the server.
Step 7 — sendevent -E FORCE_STARTJOB to restart.
Step 8 — Monitor to SUCCESS. Verify downstream jobs trigger.
Step 9 — Communicate status to stakeholders throughout.
Step 10 — Post-resolution, raise an incident ticket with RCA and preventive actions.
The golden rule I follow — never restart without knowing why it failed. Blind restarts waste time and can make things worse."

Q6. What is the difference between run_calendar and exclude_calendar?
"Both are used to control which days a job runs, but they work in opposite directions.
run_calendar is a whitelist — the job runs ONLY on the dates specified in that calendar. For example, a month-end report job would use a run_calendar that contains only the last business day of each month.
exclude_calendar is a blacklist — the job runs on its normal schedule but SKIPS the dates in that calendar. This is commonly used for public holidays — a daily job that should not run on Christmas, New Year, etc.
You can also combine both. For example — run every weekday, but exclude public holidays. In JIL that looks like:
jildays_of_week: mon,tue,wed,thu,fri
exclude_calendar: public_holidays
In a Hexaware production environment, this is heavily used for client-specific SLA-driven jobs where business calendars differ by geography or client."

Q7. A job ran successfully but the output file was not generated. How do you approach this?
"This is a classic case where AutoSys shows SUCCESS but the business outcome didn't happen. AutoSys only cares about the exit code of the script — if the script exits with 0, AutoSys marks it SUCCESS regardless of what the script actually did.
My approach:
First — I check the application log in detail. A script can exit with code 0 even if it hit a non-fatal error or warning that caused it to skip the file generation.
Second — I check the target output directory to confirm the file is truly missing and not just in a different location or with a different timestamp.
Third — I look at whether the script has conditional logic — for example, 'if no input data found, skip and exit 0.' If the upstream input file was empty or missing, the script may have exited cleanly without generating output.
Fourth — I check disk space on the output directory. Scripts sometimes silently fail to write files when disk is full but still exit 0.
The fix depends on root cause — if it's a data issue I coordinate with the upstream team. If it's a script logic issue I raise it with the app team. Then I rerun the job after the fix.
This scenario is also a strong argument for adding file watcher jobs downstream as a validation layer — don't just depend on AutoSys SUCCESS status, verify the actual output exists."

Q8. What is a global variable in AutoSys and where have you used it?
"A global variable in AutoSys is a key-value pair stored at the scheduler level that can be accessed by any job across the environment.
You set it using sendevent:
bashsendevent -E SET_GLOBAL -G "ENV=PRODUCTION"
sendevent -E SET_GLOBAL -G "FILE_DATE=20240315"
And reference it in JIL like:
jilcommand: /scripts/process.sh $ENV $FILE_DATE
Real-world usage I've seen and handled:
First — date parameters. Instead of hardcoding dates in scripts, the scheduler sets a global BUSINESS_DATE every morning and all jobs pick it up dynamically.
Second — environment switching. A global RUN_ENV=PROD or RUN_ENV=DR flag controls which database or server jobs connect to — very useful during DR drills.
Third — pipeline control flags. A global FEED_RECEIVED=YES can be set by a file watcher job and downstream jobs check this flag before proceeding.
The risk with global variables is that they are shared across ALL jobs — so changing one carelessly can impact unintended jobs. Always document and control who can modify globals in production."

Q9. How do you handle a scenario where AutoSys itself is down?
"If the AutoSys Event Server itself is down, no jobs will trigger — it's a full scheduler outage. This is a P1 incident.
My immediate steps:
First — confirm it's the Event Server and not just my client connection. I check with another team member and verify using the AutoSys admin console.
Second — check if the Shadow Event Server has taken over. In a properly configured HA setup, the Shadow should automatically promote itself to Primary within minutes.
bash# Check event server status
chk_evt_svr
Third — if Shadow hasn't taken over, escalate to the AutoSys admin team or Broadcom support immediately. This is beyond L2 scope — it needs DBA and infrastructure teams.
Fourth — while the scheduler is down, identify which critical jobs were supposed to run and assess if any can be run manually on the server to protect business SLAs.
Fifth — once the Event Server is back, check all job statuses. Jobs that were ACTIVATED during the outage may need to be force-started manually since they missed their time windows.
Sixth — communicate a full timeline to all stakeholders.
The key message here is — L2 does not fix the Event Server itself. L2's job is to minimize business impact while the outage is being resolved."

Q10. What are your best practices for AutoSys job design? (Asked to test seniority)
"This question separates someone who just operates AutoSys from someone who owns it. My best practices are:
One — Always group jobs in BOX jobs. Never have orphan CMD jobs floating around. Boxes make monitoring, control, and dependency management clean.
Two — Always set max_run_alarm and min_run_alarm. If a job that normally runs 30 minutes suddenly runs 3 hours, you want to know immediately — not at 6 AM when the business calls.
Three — Never hardcode dates or paths in JIL. Use global variables for dates and environment-level config files for paths. This makes the design portable and maintainable.
Four — Always validate output, not just status. Use file watcher jobs downstream of critical data-producing jobs to confirm the output actually exists.
Five — Use exclude_calendar for holidays. Don't rely on operators to manually hold jobs on public holidays — automate it.
Six — Document every job's business purpose in the description field. Six months later, when a job fails at midnight, you need to know immediately what it does and who owns it.
Seven — Test JIL changes in a lower environment first. A JIL syntax error in production can corrupt job definitions.
These practices ensure that the AutoSys environment is not just functional but resilient, observable, and maintainable — which is exactly what an L2 engineer is expected to deliver."

The Core Components — Deep Dive

1. 🐍 DAG Files (Directed Acyclic Graph)

"The blueprint of your entire pipeline — written in Python."


A DAG is a Python file that defines tasks and their dependencies
Airflow scans a folder (usually /dags) continuously for new or updated DAG files
The word Acyclic means no circular dependencies — Task A can never eventually depend on itself
Each run of a DAG is called a DAG Run

pythonfrom airflow import DAG
from airflow.operators.bash import BashOperator
from datetime import datetime

with DAG('daily_etl',
         start_date=datetime(2024,1,1),
         schedule_interval='0 5 * * *') as dag:

    extract   = BashOperator(task_id='extract',   bash_command='extract.sh')
    transform = BashOperator(task_id='transform', bash_command='transform.sh')
    load      = BashOperator(task_id='load',      bash_command='load.sh')

    extract >> transform >> load   # dependency chain

"In AutoSys you write JIL. In Airflow you write Python. That single difference changes everything — who owns it, how it's versioned, and how powerful it can be."


2. 🧠 Scheduler (The Brain)

"The equivalent of AutoSys's Event Server."


Continuously parses DAG files to detect new pipelines or changes
Evaluates which tasks are ready to run based on schedule and dependencies
Pushes ready tasks into the Message Queue
Does NOT execute tasks itself — it only decides what to run and when
In Airflow 2.x, the Scheduler is highly available — you can run multiple instances


"The Scheduler is stateless — it reads the DAG file, calculates what needs to run, writes it to the Metadata DB, and pushes to the queue. That separation is what makes Airflow scalable."


3. 🗄️ Metadata Database (The Memory)

"The equivalent of AutoSys's Oracle/Sybase database."


Usually PostgreSQL or MySQL in production
Stores everything — DAG definitions, task states, run history, variables, connections, XComs
The Web UI, Scheduler, and Workers all read from and write to this DB
This is the single source of truth for the entire Airflow environment


"If you want to know the status of any task, at any point in time — it's in the Metadata DB. Same concept as AutoSys, different technology."


4. 🔴 Message Queue / Broker (The Dispatcher)

"This is what AutoSys doesn't have — and it's why Airflow scales horizontally."


Usually Redis or RabbitMQ
The Scheduler pushes task execution messages into this queue
Workers pull tasks from the queue independently
This decoupling means you can add or remove workers without touching the Scheduler
Used when running the Celery Executor or Kubernetes Executor


"The queue is what turns Airflow from a single-machine scheduler into a distributed system. AutoSys pushes jobs to specific agents. Airflow pushes tasks to a queue and any available worker picks it up."


5. ⚙️ Workers (The Hands)

"The equivalent of AutoSys Remote Agents."


Workers pull tasks from the queue and execute them
Each worker is an independent process — can run on separate machines
Reports task status back to the Metadata DB
You can scale horizontally — just add more worker nodes under high load

Three executor types determine how workers behave:
| Executor | How it works | Use case |
| --- | --- | --- |
| SequentialExecutor | One task at a time, same machine | Dev/testing only |
| CeleryExecutor | Distributed workers via Redis/RabbitMQ | Production standard |
| KubernetesExecutor | Each task runs in its own k8s pod | Cloud-native scale |

6. 🌐 Web UI (The Monitor)

"Far more powerful than AutoSys's basic console."


Built on Flask — accessible via browser
Shows DAG graph view, Gantt chart, task logs, run history
You can trigger DAGs manually, clear failed tasks, mark tasks as success
Color-coded task states — green = success, red = failure, yellow = running


7. 🔔 Triggerer (Async Sensor — Airflow 2.2+)

"A specialized component AutoSys has no equivalent of."


Handles deferrable operators — tasks that wait for external events
Instead of a worker sitting idle waiting for a file or API response, the Triggerer handles the wait asynchronously
Frees up worker slots for actual compute work
Example: waiting for an S3 file to arrive — the Triggerer watches, the worker only wakes up when it's ready


How It All Flows — Step by Step
1. WRITE
   Data engineer writes a Python DAG file
   and deploys it to the DAGs folder

2. PARSE
   Scheduler detects the new file
   and parses the pipeline structure

3. SCHEDULE
   At the scheduled time (e.g. 5 AM),
   Scheduler creates a DAG Run
   and evaluates which tasks are ready

4. QUEUE
   Scheduler pushes ready tasks
   into the Message Queue (Redis)

5. PICK UP
   An available Worker pulls
   the task from the queue

6. EXECUTE
   Worker runs the actual script,
   Spark job, API call, or SQL query

7. REPORT
   Worker writes SUCCESS or FAILURE
   back to the Metadata DB

8. CASCADE
   Scheduler sees the status update,
   evaluates downstream tasks,
   and queues the next ones

9. MONITOR
   You watch it all happen in real-time
   on the Web UI

Interview-Ready Spoken Answer

"When a critical Airflow DAG fails at midnight, the first thing I do is open the Web UI and go to the Grid View — that immediately tells me which specific task failed, at what time, and whether it's a new failure or recurring pattern.
I never look at the DAG level — I zoom into the task level. Because in Airflow, a DAG failure is always one or more tasks failing. I click the red task and read the logs directly in the UI — that usually tells me the root cause within a minute.
While reading logs I'm also noting how many tasks are in upstream_failed state — those are innocent, they didn't fail, they just never ran because their parent failed. I don't touch those.
Then I check infrastructure — is the scheduler running, are workers healthy, is Redis up, can Airflow reach the metadata DB. If any of these are down, that's my root cause.
Once I've fixed the root cause and validated the fix manually, I use Clear task with downstream in the UI — which re-queues just the failed task and everything after it. I never rerun the full DAG unless necessary — Airflow gives you surgical precision and I use it.
One thing unique to Airflow — I always check the catchup setting. If the DAG was down and missed multiple runs, a naive scheduler restart can flood the workers trying to backfill everything at once. I control that explicitly.
Throughout all of this — I'm communicating. Stakeholders get an update within 10 minutes: what failed, why, what I'm doing, and when they can expect the pipeline to complete.
My rule — diagnose first, fix second, rerun third, communicate throughout."


Bonus — Airflow vs AutoSys Recovery: Key Differences
| Scenario | AutoSys | Airflow |
| --- | --- | --- |
| Rerun failed job | sendevent FORCE_STARTJOB | Clear task in UI or CLI |
| Mark done without running | CHANGE_STATUS SUCCESS | mark-success command |
| Check why it failed | autorep -d + server logs | Click task → Logs in Web UI |
| Handle missed runs | Manual force-start each | backfill command or catchup |
| Rerun only downstream | Not straightforward | Clear --downstream |
| Real-time monitoring | autorep polling | Live Web UI graph |

"Airflow gives you more control and better visibility than AutoSys during an incident — but you need to understand task states deeply, especially the difference between failed and upstream_failed, or you'll end up rerunning things that don't need rerunning and making the situation worse."
